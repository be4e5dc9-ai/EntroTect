# 2026-08-29

## provider 层整体重构（发布 0.4.4）

**背景**：Mimo 400 错误经 0.4.1/0.4.2/0.4.3 三次「收到 400 就降级重试」补丁仍未解决。

**根因**（查小米官方文档 platform.xiaomimimo.com + mimo.mi.com FAQ 确认）：
- Mimo 只接受 `thinking: {type: "enabled"|"disabled"}`，无 reasoning_effort 分档；
- 只接受 `max_completion_tokens`（不是 max_tokens）；
- 思考模式下多轮工具调用，历史 assistant 消息的 `reasoning_content` 必须回传，缺失会 400 —— 这才是三次补丁都没打中的点（补丁只改可选参数，消息里缺字段怎么降级都没用）。

**重构内容**：
- `openai-compatible.ts` 重写：请求体由 `profiles.ts` 的供应商 profile 决定（鉴权头 / token 字段 / thinking 策略 / stream_options / temperature），删除 400 猜测式降级；
- 请求走 `transport.ts`（仅网络错误退避重试）+ `errors.ts`（统一解析上游正文 + 脱敏 URL），`ProviderError` 单一定义（原来 openai-compatible 里还有一份重复定义）；
- `systemPrompt` 首次真正下发（之前 agent.ts 传了但三个 provider 都没用，等于模型一直拿不到系统提示，压缩请求同样）；
- `reasoning_content` 双向保留：流中累积 → turn-complete 带 `reasoningContent` → agent.ts 存进 assistant Message → 按 profile 回传（持久化走 messageSchema.reasoningContent，跨会话可续）；
- 空 `tools: []` 整个字段省略（严格网关会对空数组 400）；
- `profiles.ts` 补模型名兜底识别（显式 profile > providerId > baseUrl > 模型名 > generic），generic 默认保留 reasoning_content + 发 reasoning_effort；
- `anthropic.ts`：修致命 BUG —— 原来用 `readSseLines`（只吐 data: 行）读 Anthropic 的 `event:` 行，导致所有事件被丢弃、内容全空；改用 `readSseEvents`；另加 thinking_delta、system 注入、usage 分别累积；
- `google.ts`：systemInstruction 注入 options.systemPrompt；functionResponse 按工具名（原为 toolCallId，错误）；thought 部分转 reasoning-delta；
- `shared/reasoning.ts`：Mimo preset 改为 `[]`（布尔 thinking，官方无分档）；
- Composer：布尔 thinking 模型从静态「思考常开」改为可点击的 开/关 切换（小米建议在工具调用时关闭 thinking）。

**测试**：core 24 文件 / 272 用例全绿（原 260）；新增 Mimo 请求形状、systemPrompt 注入、reasoning_content 双向保留、Anthropic SSE、Google systemInstruction 等用例。

**注意**：升级前的旧会话历史缺 reasoning_content，仍可能被严格供应商拒绝 —— 建议升级后新建会话。

**环境坑**：Bash 工具跑 vitest 时 stdout 常被吞，改为重定向到文件再读；改 `packages/core/src` 后必须先 `pnpm --filter @entrotect/core build`，因为 `host-context.test.ts` 走的是 `@entrotect/core` 的 dist 产物。
