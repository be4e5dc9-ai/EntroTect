## 1. 并发编排 partitionToolCalls（toolOrchestration.ts:91）

```
[Read, Grep, Bash, Read, Edit]   （模型顺序）
  → 连续 isConcurrencySafe=true 的段分组并行：
      [Read,Grep] 并行 → [Bash] 独占 → [Read] 并行? 否——非 safe 的 Edit 前后断开
  → 并行上限默认 10（env 可调，:8）
```

- 只把**连续**的 safe 调用并行化，保持工具间的因果顺序；
- 非 safe 工具串行执行，使 `ToolResult.contextModifier` 按模型意图依序生效；
- safe 判定是**逐参数**的：同样是 Bash，只读命令与写命令可不同。

## 3. StreamingToolExecutor（同名文件）——边流边跑的状态机

状态机：`queued → executing → completed → yielded`

- **并发启动条件**（`:129`）：当前没有在跑的任务，或在跑的全部 concurrency-safe；
- **Bash 出错连坐机制**：用 child AbortController 把同批兄弟进程一并取消，但**不终止整个回合**——错误作为普通结果回喂，模型自己决定下一步；
- **降级安全**：fallback 换模型时 discard() 未完成队列，防止旧模型的孤儿结果污染新上下文。

## 4. 超时策略

- shell 默认 **120s**，上限 **600s**（`utils/timeouts.ts:2-3`，env 可覆盖）；
- schema describe 同步告知模型超时值——模型能据此主动拆分长命令；
- 长命令超时可自动转后台任务（配合 run_in_background），输出经 TaskOutput 续读。

## 5. 结果截断三道闸（constants/toolLimits.ts）★

上下文爆炸的最大来源是工具输出。三道闸按成本递增：

| 闸门 | 触发 | 行为 | 位置 |
|---|---|---|---|
| ① 单工具落盘 | 单个结果 >50k 字符 | 整块写入 `<sessionDir>/tool-results/<id>.txt`；模型只收 ≤2000 字节预览 + 文件路径 | `toolResultStorage.ts:109` |
| ② 单消息聚合预算 | 一条消息内所有工具结果合计 >200k 字符 | 从最大块开始替换为落盘引用 | `applyToolResultBudget :924`（每轮开头跑，见主循环第 2 步） |
| ③ Read 自限 | 文件读取 | 自限 25000 token / 文件 256KB；底层行级读取 readFileInRange 支持 offset/limit | `FileReadTool/limits.ts` |

设计逻辑：**生产者自限（③）→ 单块落盘（①）→ 聚合兜底（②）**，每层只在上一层失守时介入。

## 6. 自研启示

1. 先做串行执行器就能跑；并发编排（连续 safe 分组 + 上限）是第二遍加的。
2. 工具错误永远走"is_error 结果回喂"通道，类型上区分 `RespondToModel` 与致命错误的思路见 codex 笔记。
3. 截断三道闸可以直接照抄常量（50k/200k/25k-token），它们是实战校准过的。
