## 1. 分类与分组

`executeToolCalls()`（L59-101）按 `ctx.tools.executionMode(exec)` 把一个 step 内的 tool call 分组：

- **parallel**：工具声明了 `isConcurrencySafe` 且对**这组具体参数**返回 true → 连续段组成一池；
- **exclusive**：单独成屏障（前后等待）。

★ **池边界处重新分类**（"Commit before classifying again so registry changes affect unstarted calls", L84-92）：注册表变化能即时影响未开始的调用——插件在执行中途注册/注销工具立即生效。

## 2. 有界滚动池 runGroup()（L121-246）

```
fillPool():   维持 inFlight.size < maxParallelToolCalls (默认 10, constants.ts:5-6)
等待:         Promise.race(inFlight.values())   任一完成即推进
提交:         commitReady() 只沿「模型顺序」连续提交槽位
              —— pre-execute 有序、dispatch 重叠、post 与落库有序
              （注释 L215-216: "Ordered pre-execute may await; only dispatch/body overlaps"）
```

效果：并发执行不打乱模型给出的因果顺序；日志中结果顺序永远确定。

## 3. 取消语义保证重放有效 ★

abort 时的两种情况：

| 情况 | 处理 | 错误码 |
|---|---|---|
| 已启动的调用 | drain 到静默并照常提交结果 | `ABORTED` |
| 未启动的调用 | 写入**成对的合成** `tool/call` + `tool/result`（appendSkippedToolCall L249-259） | `ABORTED_BEFORE_DISPATCH` |

不变量：**日志里每个 callId 永远有配对 result**——崩溃后重放历史不会出现悬空 tool_use。

## 5. 自研启示

1. 最简版：串行 for 循环执行即可；第二遍加"连续 safe 分组并行"。
2. 并发时必须保序落库——按模型顺序连续提交，而不是完成顺序。
3. 取消路径要为未启动调用写合成配对结果，这是重放正确性的关键。
